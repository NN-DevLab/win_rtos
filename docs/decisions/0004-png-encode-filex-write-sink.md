# PNGエンコード(libpng)とFileXの間に書き込みIFを挟んで依存を分離する

- **日付**: 2026-08-10
- **ステータス**: 決定

## 背景(Context)

合成画像の保存では、libpngでPNGエンコードした結果をFileXでファイルに書き込む必要がある。libpngは`FILE*`(標準C)か自作コールバック(`png_set_write_fn`)のどちらかにしか出力できず、FileXを使う以上コールバックの実装が必須になる。

素直に実装すると、このコールバックの中で`fx_file_write`を直接呼ぶことになり、「PNGエンコードを担当するコード」が「FileX」の型・関数を直接知ってしまう。ライブラリ同士の依存は最小限にしたい、という方針をこの詳細設計の議論の中で確認した。

## 決定(Decision)

自分で定義した薄い書き込みIF(`png_write_sink_t { UINT (*write)(void *context, const GX_UBYTE *data, ULONG length); }`)を、libpngとFileXの間に挟む。

- libpngに登録するコールバックは、このIF越しに`sink->write(...)`を呼ぶだけ。FileXの型・関数は一切出てこない
- FileX固有の実装(`fx_file_write`を呼ぶアダプタ)は別ファイルに閉じ込め、IFを実装する形にする

実行時のデータの流れ(エンコードしながら逐次FileXに書き込む)は変えず、コードの依存方向だけを整理する。

## 検討した代替案(Alternatives)

- **案A: コールバックで直接`fx_file_write`を呼ぶ**: 一番シンプルだが、PNGエンコードを担当するコードがFileXを直接知ってしまい、依存を分離したいという方針に反する
- **案B: エンコード結果をメモリバッファに全部溜めてから、`fx_file_create`→`fx_file_write`(1回)→`fx_file_close`で書き込む**: FileXへの依存はエンコード完了後の別コードに閉じ込められるが、合成画像1枚分のPNGエンコード結果を丸ごとメモリに保持する必要がある。Win32シミュレータでは問題になりにくいが、将来実機(組み込み)へ移植する可能性を考えると、メモリコストの大きい方式を今から選ぶのは避けたい

## 結果・影響(Consequences)

- PNGエンコードを担当するモジュールは、FileXのヘッダ・型・関数を一切importしない
- 将来、保存先をFileX以外(例: 別のファイルシステム、ネットワーク送信)に差し替える場合も、`png_write_sink_t`を実装するアダプタを追加するだけで済む
- 抽象化の層が1つ増える分、コード量はわずかに増える(トレードオフとして許容)
- 実行時の書き込み方式(逐次書き込み)自体は変わらないため、[別名で保存のシーケンス図](../design/images/sequence-save-as.svg)の構造には影響しない
