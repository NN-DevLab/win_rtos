# 機器検索は自分のサブネット内を総当たりスキャンする

- **日付**: 2026-08-10
- **ステータス**: 別の決定に置き換え(→ [0006-fixed-ip-connect-instead-of-scan.md](0006-fixed-ip-connect-instead-of-scan.md))

## 背景(Context)

[ADR-0002](0002-ftp-discovery-http-transfer.md)で「探索(機器一覧・フォルダ一覧の取得)にはFTPを使う」と決めたが、これはFTP接続した後に一覧取得(LIST・CWD)ができる、という話であり、**そもそも同一LAN内のどの機器にFTP接続を試みるか**(IPアドレスをどう見つけるか)は別問題として未決定だった。FTP自体には「LAN内の機器を発見する」機能は無い。

## 決定(Decision)

FTP探索スレッドは、自分自身のIPアドレスとサブネットマスクをNetX Duoから取得し、同じサブネット内の全IPアドレス(例: `/24`なら最大254件)に対して、**2段階**で機器を絞り込む。

1. **ICMPエコー(ping)で生存確認**: 候補IP全件に対して`nx_icmp_ping()`(短めのタイムアウト)を投げ、応答があったIPだけを残す
2. **応答があったIPにだけFTP接続を試す**: 1で絞り込んだIPにだけ`nx_ftp_client_connect`を試み、接続できたものを「見つかった機器」として一覧に加える

pingはFTP接続(TCPハンドシェイク+FTPプロトコルのやり取り)より軽く、タイムアウトも短く設定できるため、存在しないIPに対して重いFTP接続タイムアウトを254回分待つ事態を避けられる。

## 検討した代替案(Alternatives)

- **固定のホストリストを使う**: あらかじめ登録されたIPアドレス/ホスト名にだけFTP接続を試す。シンプルで速いが、常に同じ相手にしか繋がらず、「検索」というボタン名・機能の割に汎用性が低い
- **ブロードキャストやARPで先に機器の存在を確認してから、見つかったIPにだけFTP接続する**: 一番「探索」らしい動きになるが、実装が大きく複雑になる。今回の学習用途のスコープでは見送った
- **pingを挟まず、候補IP全件に直接FTP接続を試す(当初案)**: 実装は単純だが、存在しないIPの数だけ重いFTP接続タイムアウトを待つことになり非効率。NetX Duoに`nx_icmp_ping()`([nx_api.h](../../repos/netxduo/common/inc/nx_api.h))が標準で用意されており、ping自体の実装コストが低いため、この案は見送った

## 結果・影響(Consequences)

- ping・FTP接続のそれぞれでタイムアウト値を決める必要がある(pingは短め、FTPは接続確立に必要な分)
- 全体としては「ping254回(短いタイムアウト)+ FTP接続(生存しているIPの数だけ、長めのタイムアウト)」という2段階の待ち時間になる。当初の「FTP接続254回」よりは大幅に短縮される見込みだが、体感速度は実装・実機で要確認
- 見つかった機器の一覧は、IPアドレスの配列として共有データ経由でGUIXシステムスレッドに渡す([機器検索のシーケンス](../design/images/sequence-device-search.svg)参照)
- 自分自身のIPアドレス取得に失敗した場合(ネットワーク未接続等)のエラーハンドリングは、別途検討が必要
