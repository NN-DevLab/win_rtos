# PNG保存(エンコード)にlibpngを組み込む

- **日付**: 2026-08-08
- **ステータス**: 決定

## 背景(Context)

FR9(合成画像の保存)を実現するには、メモリ上の画像データをPNGファイルとしてエンコードする必要がある。しかし、GUIXのランタイムライブラリ(アプリが実際にリンクする`common/`配下)には、PNGのデコード機能(`gx_image_reader_png_decode`)しかなく、エンコード機能は無い。

PNGエンコードができるlibpngは`guix/guix_studio/libs/libpng`に同梱されているが、これは**GUIX Studio(デザインツール)専用のビルド済み`.lib`ファイル**であり、ソースコードではない。同梱の`README.txt`にも「libpngを使うにはSourceForgeからソースを取得してビルドすること」と明記されており、このビルド済み`.lib`はGUIX Studio(64bit想定)向けのため、win_rtos(32bit/x86ビルド)ではそのまま使えない可能性が高い。

## 決定(Decision)

libpng・zlibのソースコードを公式配布元から別途取得し、win_rtos(win32/x86)のビルドに自前で組み込む。

## 検討した代替案(Alternatives)

- **簡易的な自前PNGエンコーダを書く**: PNG仕様(チャンク構造、フィルタリング、zlib圧縮)を一から実装する必要があり、実装量が大きい。libpngは実績のある実装なので、車輪の再発明を避けられる
- **PNG以外の形式(BMP等)で保存する**: 実装は大幅に楽になるが、ダウンロード画像(PNG)と合成画像(BMP)で保存形式が混在し、一貫性が失われる。アプリ名・要件定義もPNGを前提として進めてきた経緯があり、今回は見送った
- **画像そのものを保存せず「レシピ」(どの2枚をどう並べたか)だけ保存し、表示のたびに再合成する**: エンコード自体が不要になるが、既に確定した機能設計(FR9: 保存後も合成画面に留まる、一覧に1枚の画像として現れる)との整合性を優先し、今回は見送った

## 結果・影響(Consequences)

- libpng・zlibという新しい依存が増える。ソースコードを別途取得し、win32/x86向けにビルドできるようCMake設定を追加する必要がある
- ライセンス表記の追加が必要(libpng: PNG Reference Library License、zlib: zlib License。いずれも商用利用可能な緩いライセンスだが、要件定義・READMEのライセンスセクションへの追記が必要)
- ソース取得(ダウンロード)は別途、実施タイミングでユーザーの許可を得てから行う
